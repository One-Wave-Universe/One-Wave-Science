# ONE-WAVE GENERAL REFERENCE RULES

**Status:** Mandatory repository law for every AI, bridge, program, machine, document, and operator.

## 1. Single-source rule

Every durable One-Wave fact, instruction, architecture decision, bridge direction, program rule, proof status, build rule, and AI operating instruction is written **one time** into the canonical repository.

Do not maintain full duplicate copies in Downloads, Desktop, Documents, home folders, temporary folders, AI memory notes, bridge runtime directories, or secondary repositories.

Convenience locations may contain only a short pointer to the canonical repo path when absolutely necessary. They must not contain a second maintained copy of the content.

## 2. Canonical reference rule

Before acting, find and read the canonical repo file that owns the subject.

If the subject has a dedicated authority file, that authority outranks summaries, exports, old chats, local copies, cached text, generated notes, and remembered wording.

If two repo files conflict, do not silently choose. Follow the newer explicit authority chain, metadata/governance rules, and anti-drift files, then repair the conflict in the repo.

## 3. Reference-before-action rule

Every AI or program doing One-Wave work follows:

REFERENCE -> INSPECT -> ACT -> RECEIPT -> VALIDATE -> UPDATE REFERENCE

For unfamiliar or high-impact work, state the exact repo references used before mutation.

## 4. Metadata authority rule

For governed nodes, proof status, gate, lifecycle, classification, and canonical identity come from current YAML/front matter and governance authorities, especially:

`Governance_I_Series/I-06_Canonical_Node_Metadata_and_Alias_Resolution.md`

Do not reconstruct status from prose when metadata exists.

## 5. No-copy rule

Do not create a second permanent One-Wave repo checkout, exported documentation tree, ZIP mirror, runtime clone, or Downloads copy just to make a bridge/program easier to use.

Bridges and programs must point to or operate against the canonical checkout.

Temporary files are allowed only when they are ephemeral execution artifacts, receipts, caches, or detached worktrees that are not treated as a second source of truth.

## 6. No-memory-authority rule

Chat memory, model memory, human recollection, summaries, and previous messages are context only.

They never outrank the canonical repository.

If remembered information matters to a decision, confirm it against the repo before using it as authority.

## 7. One-update rule

When a decision changes, update the canonical repo authority once.

Then update references/pointers that name that authority if necessary.

Do not manually propagate full duplicate text into multiple convenience files.

## 8. Bridge rule

All bridges are transport, not authority.

Hive Pipe, ChatGPT pull bridge, GitHub Actions, Desktop Commander, SSH, Gemini, DeepSeek, Perplexity, Claude, Codex, Miniverse, and future clients must all return to the same canonical repo reference.

A bridge may carry commands, receipts, or bounded context. It must not invent or maintain its own competing project canon.

## 9. Program rule

Programs/apps may store:

- runtime state;
- logs;
- receipts;
- caches;
- ephemeral task packets;
- user-specific configuration;
- secrets outside git.

Programs/apps may not silently become the canonical source for One-Wave architecture or instructions unless the repo explicitly designates them as such.

## 10. Receipt rule

A command, test, bridge action, or remote operation is not proven by intention, queued state, documentation, or confidence.

It is proven only by a matching real receipt/output from the route that performed it.

## 11. Dead-route rule

A failed bridge is not a dead end.

Record the failure, move to the next independent authorized route, and return to the same canonical reference.

Do not solve a dead route by spawning unmanaged copies of the repo or duplicated instruction trees.

## 12. External-data rule

External scientific data remains externally sourced evidence.

Record provenance and transform instructions in the repo, but do not relabel metadata, derived encodings, or imported measurements as native One-Wave proof.

## 13. Task-branch rule

Routine modifications use a bounded task branch and PR unless a repository authority explicitly defines another safe workflow.

Do not silently change `main`.

## 14. Anti-drift rule

If a worker sees a local file, export, summary, chat, cached artifact, old branch, or generated instruction that conflicts with current canonical repo authority:

1. stop using the conflicting copy;
2. verify the canonical repo source;
3. remove or quarantine the duplicate/conflict;
4. repair the canonical reference chain if needed;
5. continue from the repo authority only.

## 15. Required first references

Every AI beginning One-Wave work should start with:

1. `GENERAL_REFERENCE_RULES.md`
2. `AI_CANONICAL_START_HERE.md`
3. the domain-specific authority for the current task
4. `Governance_I_Series/I-06_Canonical_Node_Metadata_and_Alias_Resolution.md` when governed metadata/status matters

Bridge/terminal work additionally starts with:

- `AI_BRIDGE_START_HERE.md`
- `AI_JETSON_TOOL_GUIDE.md`

## 16. Final law

**Write it once in the canonical repo. Reference it everywhere.**

No maintained convenience copies.
No competing canon.
No bridge-owned truth.
No memory-owned truth.
No unverifiable execution claims.
