# ENTER BRANCH FIRST — MANDATORY AUTHORITY FILE

THIS FILE MUST BE READ FIRST EVERY TIME THIS BRANCH IS ENTERED.

DO NOT DELETE, RENAME, REPLACE, SUMMARIZE, OR IGNORE THIS FILE.

## PROJECT AUTHORITY LAW — THE EXECUTOR DOES NOT KNOW BETTER

The executing AI does **not** know better than this project, its written plan, its branch assignment, or its accumulated repository evidence.

The executor is not permitted to substitute its own interpretation for clear project instructions. It does not get to redesign the task because another approach seems cleaner, more logical, more familiar, more conventional, or more consistent with its own expectations.

If the project gives a clear instruction, execute that instruction as written.

Do not reinterpret a branch number, project term, file name, gate, state count, architecture label, or historical note into a different assignment. Do not invent missing intent when the repository already states the intent. Do not “improve” the project by silently changing the plan. Do not decide that an old result makes the current hard start or hard stop unnecessary.

The executor's job is to **read, obey, implement, test, record evidence, and stop**. The repository files carry project memory and architecture authority. The executor does not replace them with its own memory or judgment.

Repeatedly reasserting already-written rules wastes project time and creates repair work. Misinterpreting clear instructions can damage code, delete needed history, corrupt branch purpose, create false progress, and force later branches to repair avoidable mistakes. Therefore, when a written instruction is clear, interpretation must narrow toward literal execution, not broaden into redesign.

When uncertain, inspect the authoritative project files and the branch evidence. Do not guess. If there is a real contradiction between authoritative files, record the contradiction and resolve that contradiction before implementation. A contradiction is not permission to choose whichever instruction the executor prefers.

## ENTRY LAW

When entering this branch:

1. Perform only the task assigned to this branch in `BUILD_STEPS.md`.
2. Do not make assumptions about what the branch number means.
3. Do not reinterpret the branch assignment from the master project architecture.
4. Do not replace the assigned branch task with another idea, subsystem, gate, state count, or architecture layer.
5. Do not summarize the project scope, build plan, journal, branch assignment, or rules. Read the authoritative files directly.
6. Do not skip the hard start because old progress says COMPLETE.
7. Do not skip the hard stop because code already exists.
8. Do not advance to another branch until this branch hard stop is explicitly satisfied under the current rules.
9. Do not create a new branch unless the existing build plan explicitly calls for it or a separate architecture-plan change is explicitly authorized.
10. Do not delete authoritative control files.
11. Do not treat historical notes, old completion records, old labels, or stale implementation descriptions as higher authority than the current control set.
12. If files conflict, stop implementation and resolve the conflict against the authority order below before coding.
13. Do not treat your own interpretation as higher authority than any clear written project instruction.
14. Do not spend project time creating new rules to compensate for an execution mistake when the existing rules already covered the mistake; first correct the execution and restore any damage.
15. Preserve legacy/history files required by project instructions. Cleanup means remove or correct genuinely false/conflicting material, not erase project memory.

## NO-ASSUMPTION LAW

Do not infer branch purpose from the branch number, gate number, state count, filenames alone, model memory, conversation memory, old progress labels, or previous AI interpretation. Use the explicit branch assignment in `BUILD_STEPS.md`.

## NO-SUMMARY LAW

Do not compress, paraphrase, or summarize the authoritative project files as a substitute for reading them. Work from the full text.

## BRANCH LOOP LAW

Before coding: read the authority set, confirm the exact assigned task, confirm hard start, record pre-branch analysis, inspect stale/conflicting information, and declare one exact change and one exact test.

During coding: one change at a time; test immediately; inspect evidence; record what worked, failed, and architecture effects; maximum three meaningful attempts for one approach.

Before leaving: perform cleanup check; write post-branch analysis; update diary and progress; verify prior behavior; verify no future-branch work leaked in; satisfy hard stop; STOP.

## DELETION PROTECTION

This file is permanent branch-entry control infrastructure. Cleanup tasks must never delete it.
